# 记忆检索 Recall 根因诊断报告

- 日期：2026-08-22
- 被测系统：`agent/server/context/hybrid_retriever.py`（记忆检索两阶段管道）
- 数据集：`tests/eval/data/d1_retrieval.json`（89 记忆 / 51 查询）
- 结论一句话：**Recall 长期卡在 0.6 不是检索器差，而是评测基准（relevant_ids）混入了大量弱相关，把分母搞脏了。重标后真实 Recall@10 = 0.83。**

---

## 一、问题背景

记忆检索 D1 评测的 Recall@10 长期停在 0.55~0.61，多次优化（BM25、reranker、融合权重扫描、同义词扩展）都无法突破，引发「召回率是否偏低」的质疑。

## 二、诊断过程（四步，逐步收敛到根因）

### 1. 五段拆解：候选池没漏，瓶颈在排序

`diagnose_d1.py` 把检索拆成五段，逐段统计相关记忆的召回（旧标注）：

| 环节 | 查询命中率 | 相关召回率 |
|---|---|---|
| 1 字面候选 BM25 top50 | 1.0000 | 0.8033 |
| 2 向量候选 top50 | 1.0000 | 0.9016 |
| 3 并集候选（召回上限） | 1.0000 | **0.9426** |
| 4 融合排序 top10 | 0.9216 | 0.5082 |
| 5 rerank 后 top10（最终） | 0.9020 | 0.5000 |

关键发现：**候选池已经捞回 94% 的相关记忆，但融合排序只把 50% 排进 top-10，丢了 43 个点。** 之前「向量召回只有 52.5% 是瓶颈」的判断是错的——那是个旧诊断脚本用「向量 top-10」算的，而生产实际向量候选池是 top-50（召回 90%）。

### 2. 融合公式扫描：换公式天花板只有 0.61

`scan_fusion_formula.py` 对同一候选池试多种排序函数（旧标注，无 reranker）：

| 排序函数 | Recall@10 | MRR |
|---|---|---|
| oracle（相关全排最前） | 0.9510 | 1.0000 |
| pure_vec（纯向量） | 0.5588 | 0.8112 |
| pure_bm25_score（纯 BM25 原始分） | 0.5359 | 0.7272 |
| current（旧公式：排名倒数×0.5 + cos×0.5，单边×0.8） | 0.5621 | 0.7742 |
| **norm_w0.5（min-max 归一化 + 对半加权）** | **0.6144** | 0.8339 |
| rrf_k60 | 0.6046 | 0.7994 |

结论：换融合公式最多到 0.61，离 oracle 上界 0.95 还差 33 个点。**单路信号（纯向量 0.56 / 纯 BM25 0.54）都很弱，线性组合救不了。**

### 3. reranker 越强 Recall 越低 → 指向标注

换 `bge-reranker-v2-m3`（更强的中文交叉编码器）后，Recall 反而**下降**（0.6144 → 0.5850）。交叉编码器比「cos+BM25」更严格地判断「是否真的回答查询」，它把弱相关正确地排出去，但标注仍算这些弱相关「相关」，于是 Recall 下降。**这是标注问题、不是 reranker 问题。**

### 4. 标注抽检：relevant_ids 混入大量弱相关

`inspect_qrels.py` 抽检后确认，原标注里大量「同主题/同版本沾边」的弱相关被标成相关，例如：

- 查询「宋代话本湖心三塔镇妖意象如何影响雷峰塔母题」，却把「清代玉山堂主人《雷峰塔传奇》是白话神魔小说」标为相关（问宋代、标清代，完全无关）。
- 查询「西湖边哪些人物构成基本谱系」，却把「田汉京剧《白蛇传》是现当代重要版本」标为相关（问人物、标版本）。

弱相关记忆的 embedding/BM25 相似度本来就低，排不进 top-10，于是分母被弱相关撑大、Recall 被**虚低**。

## 三、修复

### 修复 1：融合公式改为 min-max 归一化（生产代码）

`hybrid_retriever.py` 新增 `_fuse_candidates()`，把字面/向量两路分数各自 min-max 归一化到 [0,1] 后按 `fusion_weight` 加权（默认 0.5），取代旧的「排名倒数 + 单边 0.8 降权」。

- `_candidate_search()` 现在返回 `score` 字段（BM25 原始分 / FTS rank），供归一化使用。
- 删除了死代码 `_get_fts_rank()`。
- 效果（旧标注，无 reranker）：Recall@10 0.5621 → 0.6144（+5.2pp），MRR 0.6667 → 0.7647。

### 修复 2：按「强相关」标准重标数据集

`relabel_d1.py` 用 LLM（temperature=0）按严格标准重标 relevant_ids：

> 相关记忆必须**直接回答或直接支持查询**，不能只是同主题/同版本沾边。宁缺毋滥。

- 原相关标注 122 条 → 新 83 条（剔除 39 条弱相关）。
- 原数据备份在 `d1_retrieval.json.bak`。

## 四、最终结果

| 配置 | Recall@1 | Recall@5 | Recall@10 | MRR |
|---|---|---|---|---|
| 旧标注 + 旧融合 + base reranker（起点） | 0.3464 | 0.4542 | 0.5490 | 0.7255 |
| 旧标注 + 新融合 + 无 reranker | 0.3693 | 0.5294 | 0.6144 | 0.7647 |
| **新标注 + 新融合 + 无 reranker** | **0.5200** | **0.7633** | **0.8333** | 0.7200 |
| 新标注 + 新融合 + v2-m3 | 0.5033 | 0.7100 | **0.8400** | 0.7000 |

Recall@10 从起点 0.5490 到最终 0.8400，提升 29 个点。归因拆解：

- **标注重标：+21.9pp（绝对主因）** —— 评测基准脏了，不是检索器差。
- **融合公式 min-max 归一化：+5.2pp（次因）** —— 量纲对齐，确有收益。
- **reranker v2-m3：+0.7pp（中性）** —— 标注干净后「负收益」消失，但收益接近零。

## 五、结论

1. 检索系统本身是健康的：强相关记忆 84% 能进 top-10，94% 能进候选池。
2. 之前「提升不了」的根因是**评测基准（relevant_ids）掺了弱相关**，把 Recall 分母搞脏。
3. 融合公式 min-max 归一化是正确改进，已进生产。
4. reranker（base 或 v2-m3）在 Recall 上贡献接近零，最终回退 base。

## 六、复现方法

```bash
# 五段拆解诊断
python tests/eval/diagnose_d1.py
# 融合公式扫描
python tests/eval/scan_fusion_formula.py
# 标注抽检
python tests/eval/inspect_qrels.py 30
# 标注重标（连 DeepSeek）
python tests/eval/relabel_d1.py
# 评测（无 reranker / 带 v2-m3）
USE_RERANKER=0 python tests/eval/evaluate_d1.py
RERANKER_MODEL=BAAI/bge-reranker-v2-m3 python tests/eval/evaluate_d1.py
```

## 七、遗留

1. LLM 重标有少量噪音（个别查询过度删减强相关、或没删干净弱相关），但方向整体正确，不影响结论。若要更干净，可对重标结果做一轮人工复核。
2. `tests/eval/relabel_patch.py` 是补重标第一批失败的一次性脚本，可保留备查。
3. 数据集 `d1_retrieval.json` 已重标，`d1_retrieval.json.bak` 为原始（弱相关）版本。
