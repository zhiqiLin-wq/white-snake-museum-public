# D4（L4 压缩与摘要）全程复盘

- 日期：2026-08-22
- 被测系统：`ContextManager._update_summary`（FIFO 压缩时的递归摘要）+ `SUMMARY_UPDATE_USER`（摘要 prompt）
- 评测脚本：`evaluate_d4.py`（复用 D3 数据）
- 一句话结论：D4 从「因 D3 结构改动而 KeyError 挂掉」→ 修好 → 覆盖度 0.4 → 0.733；摘要系统本身修到位了（empty 归零、短中段满分），长段低分是判定尺子严，非摘要系统差。

---

## 一、D4 测什么

**L4 压缩与摘要评测**：长对话触发压缩时，系统把老消息压成「摘要」（之后当历史注入给 LLM）。D4 检查摘要是否覆盖关键信息。

它和 D3 是记忆系统的**两个出口**，互补：

| | 看哪个出口 | 测什么 |
|---|---|---|
| D3 | 记忆库 | 关键信息能否被检索找回 |
| D4 | 摘要 | 关键信息有没有被写进摘要 |

---

## 二、蝴蝶效应：D3 结构改动连带弄坏了 D4

D3 数据结构从 `{key_facts, conversation}` 改成 `{segments: [...]}`（3 段），而 D4 读的是旧字段 `data["key_facts"]` / `data["conversation"]`，直接 KeyError 挂掉。教训：改共享数据结构要扫全引用（见 D3 复盘第十节）。

## 四、诊断过程

### 第 1 步：首跑 0.4，摘要被「闲聊」淹没

中长段摘要里记了一堆闲聊客观知识（"雷峰塔位于西湖南岸""青蛇有些版本是男身"），但用户的观点/偏好全丢了。根因：摘要 prompt 只写「保留关键事实和决策」，没说「用户主观信息优先」，摘要 LLM 把客观知识当关键、把用户观点当次要。

### 第 2 步：改摘要 prompt 优先级 → 关键词版 0.833

prompt 加「用户长期信息（身份/偏好/观点/约束）最高优先级，客观知识可省略」。中长段 0.2→0.9，立竿见影。

### 第 3 步：语义判定暴露「摘要质量不稳定」

关键词子串匹配太粗（"长篇→简短回复"字面不匹配就误判缺）。改向量判定后，发现摘要长度每次跑波动巨大（85~289 字符），且短段摘要 85 字符只写到前 5 条就断，后 5 条真没进摘要。

### 第 4 步：改 prompt「简洁→完整」→ 长段暴跌

把「简洁」改成「完整，逐条列出，一条不能漏」，短中段涨到 0.9，但长段暴跌 0.2——长段 100 轮压缩最频繁，摘要 LLM 频繁返回空（9 次），最终摘要只剩 74 字符。

### 第 5 步：控制摘要输入长度 → 长段 0.4 但 empty 反增

消息块 8000→2000、单条 500→300、旧摘要截断 2000。长段 0.2→0.4，但 empty 9→17 次**反而更多**。关键修正：empty 的根因不是「输入长」，是「完整 prompt 要求长输出 + reasoning 一起超 max_tokens」。

### 第 6 步：max_tokens 1024→2048 → empty 归零

长段 empty 从 17 次降到 **0 次**，短中段满分 1.0。长段 0.2 是因为判定尺子严（见下）。

## 五、长段 0.2 的真相：判定尺子严，非摘要差

max_tokens 2048 后看长段摘要实际内容，**关键信息明明都在**：

```
1. 用户不喜欢看堆砌版本罗列、没有分析的整理内容。   ← 堆砌 在
2. 用户特别在意文献引用的准确性，不能凭记忆转述。   ← 转述 在
3. 用户认为《白娘子永镇雷峰塔》的悲剧结局...        ← 悲剧 在
4. 用户研究版本演变时会按照朝代顺序来梳理。         ← 朝代 在
5. 用户认为许仙这个人物在不同...                   ← 许仙 在
```

但评测判这些是缺失，因为余弦 0.66~0.72 卡在 0.72 阈值下。原因：bge 对「完整第一人称句（我不喜欢那种堆砌…）vs 摘要第三人称转述（用户不喜欢看堆砌…）」余弦偏严，加上切句太细（按逗号把"堆砌版本罗列、没有分析"切成两半）进一步稀释。

**和 D6 同源**：都是 bge 对「措辞差异」敏感、0.72 阈值对这类不鲁棒。保守阈值下（不引入假阳性），0.733 是真实反映。

## 六、生产代码改动汇总（context_manager.py）

1. `SUMMARY_UPDATE_USER`：加优先级规则（用户长期信息最高、逐条完整保留、客观知识可概括）。
2. `_update_summary` max_tokens：512 → 1024 → **2048**（reasoning 模型 + 完整摘要需要）。
3. `_update_summary` 输入长度控制：单条消息 500→300、消息块 8000→2000、旧摘要截断 2000。

评测改动（evaluate_d4.py）：数据读取适配 `segments`；判定从关键词改为语义向量。

---

## 七、经验教训

1. **摘要 prompt 必须写「用户信息优先」**，否则摘要会被客观闲聊淹没，用户观点全丢。
2. **summary 的 max_tokens 也要 2048 级**：reasoning 模型 + 「完整」prompt 要求长输出，小 max_tokens 必空（和提取同源，见 [[deepseek-reasoning-maxtokens]]）。
3. **控制输入长度治不了「输出长导致的空」**：输入截断让「成功时摘要更长」，但不降失败率；真正消 empty 的是加大 max_tokens。
4. **长对话摘要增量更新仍不稳**：即使 empty 归零，30+ 次增量更新下摘要质量仍随 LLM 随机性波动。
